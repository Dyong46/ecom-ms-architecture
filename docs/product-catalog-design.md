# Product catalog: SPU/SKU with UUID identifiers

Status: Accepted. Date: 2026-11-18. Decision owner: project owner.

## Selected scope

The owner selected the five-model Product/ProductVariant/Option/OptionValue/explicit
join design, UUID strings for all new entity IDs, a clean-data start, hard deletion
with cascade, and service-level validation of variant combinations. Purchase APIs
change to SKU UUIDs and integer quantities without compatibility with the old API.
OrderLine stores a snapshot of the purchased item.

Product remains the owning service. Search still uses Elasticsearch directly in
Product with after-commit updates and explicit reindex recovery. Search indexes
one document per SKU with its own attributes, then groups matching hits by SPU;
see [SKU search design](product-search-design.md). No support module,
Kafka, outbox, generic search facade or inventory service is added for this work.

## Data model

```text
Product (SPU) → ProductVariant (SKU) → ProductVariantOptionValue
                                             ↓
Option → OptionValue ←────────────────────────┘
```

- Product: UUID ID, name, unique slug, nullable text description, created/updated timestamps.
- ProductVariant: UUID ID, globally unique SKU code, decimal(12,2) price, integer stock,
  owning Product and timestamps.
- Option: UUID ID and globally unique name.
- OptionValue: UUID ID, value unique within its Option, optional JSON synonyms.
- ProductVariantOptionValue: composite primary key `(product_variant_id, option_value_id)`.
  No extra surrogate ID, optionId or variantKey is introduced.

All four standalone IDs are generated by Hibernate using `GenerationType.UUID`,
represented as Java String/JSON string and persisted in `varchar(36)`. Order IDs
and OrderLine IDs retain their existing integer types. The SQL Option table is
`product_option`, and the OptionValue value column is `option_value`, avoiding SQL
keyword collisions. The old Category/price/stock-on-Product model is replaced.

A Product may initially have no variants. A SKU without option selections is the
default variant; only one such combination is allowed per Product. Price may be
zero; negative price/stock and fractional stock are rejected at the API/service
boundary. JSON fractional quantities are rejected rather than truncated to int.

The service rejects missing/repeated option values, two values from the same Option,
and duplicate combinations regardless of selection order. Adding a variant locks
its Product row before checking combinations, serializing concurrent additions
across service instances. The database enforces the selected SKU/slug/option-name,
option-value and join-key uniqueness, but does not enforce whole-combination
uniqueness or one-value-per-option as additional constraints.

## Deletion and accepted trade-offs

Product deletion physically removes its SKUs and join rows. Option deletion removes
its values and all their join rows; deleting a value removes its join rows. SKUs
referencing a deleted value remain, with fewer selections. This is the owner's
selected cascade behavior, rather than Restrict/soft deletion.

Consequently, deleting shared options can leave existing SKUs with incomplete or
identical combinations. Creation/addition validation does not repair those SKUs.
Direct SQL imports also bypass service combination validation. Review affected
SKUs after option deletion; stronger database constraints/reconciliation are out
of scope for this selected model.

## Purchase and order snapshot

```json
[
  {"skuId":"c6816e51-a533-416b-8bc4-df73421cc412","quantity":2}
]
```

Both `/api/v1/products/purchase` and `/internal/products/purchase` retain the array
envelope, but require `skuId` and positive integer quantity. The old numeric
`productId` purchase contract is not supported. Order's `products` array uses the
same new SKU request contract through `proxy-module`.

Product locks requested SKU rows in sorted ID order, validates the complete batch
and decrements only the requested SKU stock in one local transaction. Missing,
duplicate, insufficient-stock or invalid-price SKUs reject the batch. Responses
include Product ID, SKU ID, SKU code, Product name/description, selected option
name/value map, unit price (`price`) and requested quantity.

Order verifies response SKU identities/quantities against the request and saves
OrderLine snapshots from trusted Product responses: Product ID, SKU ID, SKU code,
name, options as JSONB, unit price and integer quantity. There are no cross-service
foreign keys. Notification uses the same snapshot wire shape and renders SKU and
selected options in confirmation email.

This does not add distributed rollback, reservations or purchase idempotency. The
existing behavior of stock reduction before Order/Payment completion remains;
transactional outbox/saga/reservation work remains separate.

## API usage

For a ready-to-import sample catalog with 50 SPUs and 323 SKUs, see the
[JSON importer and usage guide](../scripts/README.md). It uses these APIs and
resolves named options to UUIDs without direct database writes.

Existing Product read/write authentication rules remain. Option management requires
authentication. Gateway forwards `/api/v1/product-options/**` to Product; the public
GET route remains limited to `/api/public/v1/products/**`.

1. `POST /api/v1/product-options` with `{"name":"Color"}` returns its UUID.
2. `POST /api/v1/product-options/{optionId}/values` with
   `{"value":"Blue","synonyms":["azure"]}` returns the value UUID.
3. `POST /api/v1/products` with:

```json
{
  "name":"Phone A",
  "slug":"phone-a",
  "description":"Example SPU",
  "variants":[
    {
      "sku":"PHONE-A-BLUE",
      "price":199.90,
      "stockQuantity":10,
      "optionValueIds":["c6816e51-a533-416b-8bc4-df73421cc412"]
    }
  ]
}
```

Use the OptionValue UUID returned in step 2, not the example UUID above. Product
creation returns the SPU UUID. `GET /api/v1/products/{id}` returns nested SKU IDs,
codes, prices, stock and selected options as DTOs without ORM cycles.

Other initial endpoints:

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/api/v1/products?page=1&size=20&name=Phone` | Paged Product DTOs; optional name filter |
| POST | `/api/v1/products/{id}/variants` | Add a SKU using the variant request above |
| DELETE | `/api/v1/products/{id}/variants/{skuId}` | Delete a SKU belonging to that Product |
| DELETE | `/api/v1/products/{id}` | Delete the SPU and its SKUs |
| GET | `/api/v1/product-options?page=1&size=20` | Paged options and values |
| DELETE | `/api/v1/product-options/{id}` | Delete an option, values and join rows |
| DELETE | `/api/v1/product-options/{id}/values/{valueId}` | Delete a value belonging to that option |

The old raw `/products/{id}/entity` route is removed. Editing SKU identity/options,
price/stock management APIs, category modeling and required Product option axes
are not introduced in this initial scope.

## Fresh databases and search reset

This is a breaking clean-data baseline, not an in-place conversion of old IDs.
At the owner's request, Product migrations are consolidated into the single
`db/migration/V1__init_catalog_schema.sql` baseline. The old Product schema,
seed-data, auditing and stock-update migrations are removed. Product uses Flyway's
standard `db/migration` location without a custom location override. Order is
consolidated likewise into `db/migration/V1__init_order_schema.sql`, including SKU
UUID references, integer quantities and purchase snapshots; the old Order schema
and separate migration location are replaced. Empty databases start with the new
schemas and no seed catalog data. Existing Flyway histories must not be repaired
to mark old tables as this schema.

Before starting the new services against existing local data:

1. Stop Product, Order and producers/consumers of old purchase events. Finish or
   discard old test orders/events/jobs as appropriate for the local environment.
2. Reset the Product and Order database schemas **including their Flyway history**,
   or provision new empty databases and point the services to them. This erases old
   Product/Order data; no ID conversion or historical snapshot reconstruction is provided.
3. The current SKU search uses a separate `products_v2` index; populate it with
   reindex after the services restart. The old `products` index is unused by the
   new code and can be removed separately once old applications are stopped.
4. Restart Config Server/Gateway/Product/Order/Notification with the changed contracts.
5. Create the catalog via API, or import UUID-based data, then run the authenticated
   `POST /api/v1/products/search/reindex` for any data imported outside Product APIs.

No live database, Kafka backlog, Mongo job collection or Elasticsearch index is
reset automatically by this change. The exact environment to erase was not supplied.
Use [Product search design](product-search-design.md) for Elasticsearch setup and
maintenance/reindex limitations.
